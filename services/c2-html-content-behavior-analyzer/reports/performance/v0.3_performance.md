## Reading

- NFR1 with XLM-R: end-to-end p95 3,996 ms vs 5 s → MET (18/19 URLs ≤ 5 s; network time dominates the tail).
- NFR1 without XLM-R: end-to-end p95 3,537 ms vs 5 s → MET (19/19 URLs ≤ 5 s; network time dominates the tail).
- NFR5 with XLM-R: peak 1.49 req/s at 20 clients (p95 31,143 ms); more clients only queue (throughput flat, latency grows, 6 request(s) hit the 30 s budget at the highest level). 50 URLs/s is a SERVER-scale target: it would need ≈ 34 such processes (e.g. one per core on several machines behind a load balancer) - NOT met on one laptop process.
- NFR5 without XLM-R: peak 3.34 req/s at 1 clients (p95 1,031 ms); more clients only queue (throughput flat, latency grows, 1 request(s) hit the 30 s budget at the highest level). 50 URLs/s is a SERVER-scale target: it would need ≈ 15 such processes (e.g. one per core on several machines behind a load balancer) - NOT met on one laptop process.
- Horizontal scaling needs: the in-process pieces moved out - SQLite results store → PostgreSQL, in-process queue / worker → a shared queue (Redis / RabbitMQ) with separate worker processes, the per-process result cache and rate limiter → Redis, the SSE event bus → pub/sub; each process loads its own models (~878 MB RSS for the largest configuration measured), so RAM per box limits processes per box. url mode adds network time per request, which is I/O-bound and overlaps well across threads.
